# 货币战争重启开发记录

## 2026-10-29：当前费用刷新与连续交易收据

参考三月七`buy_aglaea`、`buy_seele`按核心／等级切换刷新阶段的机制，接入[标准刷新](../autohsr/currency_wars_standard_refresh.py)，策略版本为`standard-native-v2`。不新增CLI参数，仍使用本局冻结的默认／阿格莱雅／希儿策略；现有日常、差分和独立UI工作未改动。

- 先购买已识别的合适报价；每次购买仍收店重采。完整阵容已上场、存在备战空间且当前阶段适合寻找角色时才考虑刷新。希儿参考无核心6级、未三星7级、三星9级的阶段；阿格莱雅继续寻找核心和缺失协同角色。能够支付完整一级经验时优先保留这笔成长预算。
- 刷新费用读取当前按钮独立字段，接受明确0～99，不把基础规则2当作本次费用。缺读时原色／二值图OCR须高置信度一致；已有冲突或不支持的读数不覆盖。每节点最多六次、累计十二金币；刷新次数和费用从已核实收据统计，收店重开不能重置额度。非紧急余额保留10金币，收费刷新另留至少1金币购买余量。
- 费用、五格当前报价和备战席签名写入意图后，经Context同账号、版本、新鲜画面和再推导校验，仅点击一次刷新。连续两帧核对金币恰好扣除当前费用、至少一格报价改变、刷新后五格名称及价格完整、等级／经验／概率不变、备战席不变，才生成财务收据。
- 空报价必须对应同节点、最近刷新后已核实购买的位置，不能将漏识别当作售罄。所有五格确已买空时也允许刷新，但刷新后的五格必须完整可读。免费刷新或收费后报价完全相同时仍保持未知，当前没有足以独立确认这类结果的反馈契约。
- 保存原始开店前快照；后续使用开店→各次刷新收据的连续余额与报价，给新观察的金币／报价／经验单独附来源。刷新后购买按实际新余额计算；收店返回同节点的新余额并保留未变阵容。unknown、暂停、换号、写账失败均不重放刷新。

验证：本轮增加15项专用机制检查，覆盖真实脱敏商店费用、0／1／2／6／12费用、缺读和冲突、成长阶段、备战空间、全售罄、跨次开店上限、连续收据与后续购买、错误扣款／报价／经验／概率／备战变化、真实Context单次输入、两帧反馈、未知不重放、暂停／换号／落盘失败。除保存的费用2外，其他费用及刷新后页面均为合成变体，不能记作真实刷新成功。

全量**1117项单元测试通过**，`runs/currency-standard-refresh-final-tests.log`；**83项假后端GUI检查通过**，`runs/currency-standard-refresh-gui.log`。包含“UX/UI”本轮已提交的输入反馈修复。两份历史画面`101-shop-before-buy`与`114745_408770_currency_standard_shop_reconciled`删除费用OCR后，经过本地实际字段OCR均重读为2；原PNG和样本SHA-256不变，结果`runs/currency-standard-refresh-replay.json`。两份用于字段校准及历史回放，没有训练模型或新增独立留出。未启动、检测或操作游戏，未新增资源消耗、未接续旧局；本后端开发未构建EXE，打包状态由UI工作单独记录，独立整局计数仍0/10。

出售、装备、投资及其他特殊节点仍待接通。额外赠送金币／经验的刷新效果尚无专用核验，遇到这种变化保留原意图并停止；本轮实现不能外推为所有环境或整局已支持。

## 2026-10-29：满员阵容交换与双向身份核验

参考三月七`deploy_and_optimize`、`move_character`对已持有角色重新分配和成对交换的机制，新增[标准满员交换](../autohsr/currency_wars_standard_exchange.py)。保留现有资源、版本、账号和输入代次门禁，没有启动游戏或接续历史开发局。

### 已接入的行为

- 在已采集完整且合法的满员阵容中，比较备战角色替换在场角色，以及前后台角色互换。只采纳评分严格增加且不造成同名上阵、位置不适配或缺前台的候选，反向交换不会因同一组事实再次成为增益。
- 评分复用已有星级、费用、标签重合及本局核心偏好；希儿在适配允许时优先前台，阿格莱雅策略下参考上游的风堇前台条件。是待实战校准的局部评分，不是最优全局阵容或胜率承诺，装备尚未完整纳入评分。
- 输入绑定本次实际来源／目标槽、角色与头像签名，经Context重新推导、UID和落盘意图校验后仅拖动一次。原有释放鼠标、暂停和失焦机制继续共用。
- 返回相同节点、金币、生命、等级和人数的可查看备战页后，仅进入身份核验。此时`exchange.status=verifying`，原动作的`movement_verified=false`；不会因为画面返回、人数不变或头像相似就认定换人成功。
- 接着分别打开两个受影响位置的角色面板，读取名称、星级、费用和实际位置适配。两边均符合预期，且分别关闭回相同备战页，才设置`movement_verified=true`与`exchange.status=verified`。同名高星替换也强制读取两边星级；其余角色只保留图像未变的身份，不把旧位置的装备或身份套到新角色上。
- 核验期间仅允许对应角色的查看和关闭。身份不符会记录实际角色并停止，未知或中断不重复拖动；核验最多六次查看。暂停／接续后按输入代次和运行目录淘汰旧面板位置证据，先关闭旧面板，再从当前备战页重新定位。
- 同时修复经验支付意图落盘后被自身pending账本挡住的问题。动作再推导只投影当前已落盘意图，结果必须与该意图的动作、预期和目标一致；旧unknown不参与这种投影，也不获得重放资格。

### 验证及限制

- 全量**1095项单元测试通过**，`runs/currency-standard-exchange-tests.log`；**83项假后端GUI检查通过**，`runs/currency-standard-exchange-gui.log`。
- 本轮新增9项检查。真实Context加假窗口验证一次拖动、两次打开及两次关闭、独立角色字段解析、同名不同星级、前后台互换、无效拖动不会变成成功、对账变化、来源篡改、暂停／跨运行证据失效、查看次数上限及经验支付的完整重推路径。图像与窗口均为合成／假后端，不是新的实机或独立留出样本。
- 仅覆盖已支持的标准六格后台与合法满员阵容。无前台、不适配或角色事实缺失仍停止；任意全局重排、刷新／出售、装备策略及所有特殊节点还未全部接通。没有新增资源消耗或实机整局，历史独立通关仍0/10，旧十场目标未恢复。

## 2026-10-28至10-29：标准购买、经验与三种决策策略

本轮把三月七的“核心角色优先→根据已持有核心切换成长阶段→购买后重采角色”和“先核算支付到下一级所需经验”的思路接入标准流程。参考版本、源文件Git blob与GPL v3许可见[来源说明](../assets/upstream/March7thAssistant/README.md)。这是原生适配，尚未完整复现上游整套阵容、装备及刷新路线。

### 行为变化

- 标准商店按当前可见售价选择候选，名称、星级、费用档位分开，不用角色名字推断固定费用。已采集完整持有阵容后才能交易；当前窗口、账号／输入代次、客户端4.6、开店前局面及备战席签名须一致。旧超频购买仍保持1～5售价限制。
- 默认策略考虑缺少的不同角色、已有角色积累和可见羁绊；阿格莱雅／希儿另有核心与协同角色偏好。已有角色补空位也使用本局策略偏好，并保留唯一名字、位置适配和前台要求。满员阵容替换仍未接通。
- 非紧急且金币至少10时保留10局内金币；低生命或不足10时允许使用现有余额。评分扣除可推导的标准利息损失，是待校准的工程权重，不是最优收益承诺。
- 每次仅买一张，保存意图后再输入。核对同节点、同等级、所选卡片消失、其他候选不变、金币精确变化及备战图像变化，连续两帧通过后生成收据。随后收店、丢弃旧阵容采集，重读实际角色和星级，再决定下一笔；不提前宣称已升星。
- 购买经验先核算本级剩余经验及整级费用，余额不足时不零散垫付。每次只支付4金币，再核对经验增加4或带完整等级／满级标记的最终升级。升级新增容量后重新观察商店和部署；不能连续盲按F。
- 账本新增交易收据校验，单纯`status=verified`不足以放行后续动作。未知、暂停、换号、写入失败都保留原意图，标准接续仍不重放未知交易。同时补齐节点继续、下一位面等新免费动作的账本识别，避免后续节点被旧免费动作白名单挡住。
- 标准开发单次步骤上限为512，仍有界；原40步上限不足以容纳多轮角色采集。它不是新增对局预算，也不自动继续旧开发局。

CLI可在新局选择`--currency-strategy default|aglaea|seele`；不填时新局为default，接续沿用记录。策略冻结在本局会话，显式不同的接续策略会报错，运行覆盖不保存日常配置。例如：

```powershell
.\.venv\Scripts\python.exe -m autohsr --currency-wars-standard --currency-strategy aglaea
.\.venv\Scripts\python.exe -m autohsr --currency-wars-standard --resume-active-currency
```

以上是操作方式说明，本轮没有执行这些实机命令。GUI选择器由“UX/UI”对话按同一Runner接口整合；当前源配置和日常、周常入口保持各自范围。

- 本轮新增19项专用检查，包含三种策略阶段、完整阵容与空间、未知售价、整级费用、满级变体、实际Context输入链路、两帧交易反馈、收店重采、交易收据损坏、暂停、换号、落盘失败和未知交易不重放。0／6／12金币售价、满级等变体是合成机制检查；真实商店文字回放中的售价为1，不能将合成变体记作实机交易验证。

## 2026-10-28：节点编号修复、标准继续与结算链

本轮在保留原生玩法和当前AutoHSR交互的前提下，参考[三月七货币战争](https://github.com/moesnow/March7thAssistant/blob/7cf6c6bed474539485d3b1504077ac352866829f/tasks/weekly/currency_wars.py)的局部字段识别、阶段观察和分段流程组织。没有复制其角色费用表、自动放弃旧局、失败重开或通用确认行为，也没有直接执行已安装的三月七程序。

### 已实现

- 战斗节点先定位图标框右边界及节点／百分比之间的短分隔线，再读取完整编号；原色与阈值化读数必须一致。支持语法中的两位数编号，不能通过截断`1-10`修复`1-1`。分隔线缺失、多个候选、读数冲突或置信度不足时保持未知。
- 原始全屏OCR保留，新增字段读取单独随隔离OCR结果及样本保存。旧样本仍能加载，历史单调时间戳仍不作为新鲜画面。短暂缺读只有限观察；明确读到另一节点则停止，均不重发出战。
- 标准节点的“继续挑战”绑定已经落盘并核实的出战及同编号胜利。反馈只接受同位面紧邻下一节点，或唯一高亮的下一位面；跳号、旧节点、冲突位面不算推进成功。保存逐节点历史。
- 支持已核实节点推进后自动展开的商店收起，核对到达来源、节点、金币和等级，再采集新备战阵容。该动作不购买或刷新。
- 下一位面导航绑定本次继续动作，后续环境确认核对对应位面的起始节点；未接通的投资／特殊节点仍停在明确的未支持边界。
- 第三位面对应最终节点的胜利，可以接续四步结算：最终胜利→评级→摘要→统计→大厅。每一步分别保存意图和反馈，缺前一页面证据、跳步、未知输入或账号变化不能标记整局完成。完成字段仍带`development_only=true`，开发接续不计入独立验收。

实现入口为[节点字段读取](../autohsr/currency_wars_node_ocr.py)、[标准推进](../autohsr/currency_wars_standard_progress.py)及[标准流程](../autohsr/currency_wars_standard_flow.py)。现有CLI、GUI入口和默认资源设置未改变；没有修改“UX/UI”对话负责的界面文件。
