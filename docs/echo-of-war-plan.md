# 历战优先周计划

更新日期：2026-10-30。借鉴三月七的历战优先顺序，将当前周额度检查、有限挑战与后续清体力接入AutoHSR原生[体力计划](power-plan.md)。桌面在“设置 → 体力计划”接入历战开关、副本／地点及开始星期；新版原生视觉与真实组合仍待验收，本轮没有启动、检测或操作游戏。

## 如何执行

运行顺序为**到期历战 → 用户体力计划条目 → 已开启的默认副本补刷**，全过程使用原日常Runner及一份已有资源预算。不会为历战另外取得240开拓力，不补燃料、星琼或后备体力；已有沉浸器仍由原计划单独冻结和记账。历战前先核对当前剩余0～3次领奖额度，再按当前余额和本次预算分配挑战；每次价格和结算继续经过原副本门禁。

| 设置 | 默认值 | 含义 |
| --- | --- | --- |
| `echo_of_war_enabled` | `false` | 是否加入历战优先阶段；仍须本次显式启用体力计划 |
| `echo_of_war_start_day` | `1` | 从本游戏周星期几04:00起到期，1～7 |
| `echo_of_war_target` | `毁灭的开端` | 原计划目标名称，执行时重新核实 |
| `echo_of_war_location` | `支援舱段` | 明确地点，不能由同名第一项替代 |

没有创建定时任务或系统唤醒。开始星期表示**点击开始后是否把历战加入本次计划**，不会等到某个时间自动运行。资格使用日常原报告的开始时间，游戏周从北京时间周一04:00起算；例如星期五03:59开始、04:10才到刷本阶段，原本未到期的星期五目标仍不临时加入。尚未结束的历战阶段跨游戏周时停止，不在同一运行重建新周额度；已结束的阶段不会因后续普通刷本恢复而再开新周。

读取到0次时，核实该页面并记录目标周额度已用尽，本次历战完成数保持0；不写成本程序打了3次。余额只足够两次时，可确认两次并保留当前目标周剩余次数，剩余本次资源可按用户条目／默认副本继续使用。下一次明确开始时重新核对当前账号、游戏周与真实周额度，不依赖配置中的全局时间戳。

只有再次读到可核实的0次，才将历战状态记为complete。本次完成数只来自本运行已核实支付和结算，其他原因造成周额度减少不增加该计数；额度增加、无法读取、换号或证据冲突均停止，不把它们当作新额度或已完成。手动加入体力计划的历战条目也先受当前可用周次数限制，不能按长期目标直接分配3次。

正数周额度绑定实际读取它的原指南截图；进入挑战页后核对同一账号、输入代次和支付进度，不把不含周次数的挑战页截图冒充数值来源。暂停后代次变化会重新核实指南，旧来源不能授权付款。最终0次仍用当时实际显示该字段的指南画面单独证明。

## 入口与保存

以下是用法说明，本轮没有执行这些游戏命令：

```powershell
# 空条目列表也可以启用历战；完成后按原默认副本补刷本次剩余预算
.\.venv\Scripts\python.exe -m autohsr --run --power-plan --echo-of-war
# 本次只做已开启的日常项与历战，不补刷默认副本；历战从周五04:00起到期
.\.venv\Scripts\python.exe -m autohsr --run --power-plan --echo-of-war --echo-start-day 5 --no-fill-power-plan
# 在原日常／周常计划中加入历战优先；到期差分或货币战争仍在日常完成之后
.\.venv\Scripts\python.exe -m autohsr --plan --power-plan --echo-of-war
```

`--echo-target`、`--echo-location`可覆盖本次目标；`--no-echo-of-war`在本次关闭该阶段，此时仍须有有效用户条目。参数只用于`--run/--plan --power-plan`，不用于仅补领奖、只接续原周常或检测。运行与CLI覆盖不保存设置，只有保存设置才持久化偏好。

普通`Runner`调用保持单副本原义，存有历战偏好不会让旧GUI隐式扩大执行范围。界面调用沿用`Runner/PlanRunner(...,use_power_plan=True)`；历战启用时，`power_plan=[]`是有效配置。它属于日常刷本的优先阶段，不增加现有`weekly_mode`的差分／货币战争选项。

## 记录和交互

`report.power_plan.weekly_echo`包含开始星期、原开始时间、目标周、到期时间、目标、最多3次、本次`completed`、周额度观察及状态。状态包括not_due、waiting、active、complete、limited、partial；limited表示本次可用预算不足以继续，不表示该周已经完成。`completed`不是历史累计，也不是从3减去当前额度得到的推测值。

历战付款使用`power_plan.charges`中的`row=-2`，用户条目仍是0起的索引，默认补刷为-1。资源、全局次数和历战本次次数在原`battle-session.json`同一笔提交；写入失败恢复为原待核对状态，后续不重发，原已核实历战也不会被后续普通副本失败抹掉。旧体力计划没有此字段的记录仍可核对，用户长期条目的`before/done`不因启用历战或换周重置。

运行事件`power_plan_progress`新增weekly阶段及可选`weekly_echo`摘要，保留原目标周、due、target、maximum、completed、remaining和state，不带账号或证据路径。remaining可由已知额度减去本次已核实挑战得出；不能只因为它为0就点亮完成，complete仍要求新的0次页面证明。首页在未核实当前账号前只显示计划预览，结果页说明对应的原目标周，不把旧周结果当作当前周事实。

新体力归档目录的账号和目标键各缩为摘要前32字符，完整64字符仍在账本逐份核对。这解决普通Windows用户目录下追加目标／运行ID后可能超过路径长度的问题；原完整键目录继续原位使用，同归属同时出现两个布局则停止。没有迁移、覆盖或删除旧进度。
