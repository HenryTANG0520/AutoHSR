# 多副本体力计划

## 2026-11-06 多副本的当前余额核验

体力计划用当前同账号画面判断每项是否可负担。账号核验先检查同一区域已读的全部 UID 文字，再按原置信度核实唯一完整账号。余额或账号未核实时停止后续刷本，保留已结算的历战、计划条目和资源记录。

首次打开挑战页和实训支援核验后重新打开时，读到同样已核实的低余额均将当前普通副本记为延期。开启补刷后可按原预算改刷能支付的默认副本。调整挑战轮数后使用新画面收紧本批上限。队伍页余额低于已核实费用，或余额区域出现 `2O/300`、残缺数字、缺值标签和冲突读数时，在写支付意图前停止。旧空布局继续核对原挑战页费用和当前队伍、账号。

普通体力计划写入本批支付意图后，在 Windows 发送前再次核对当前队伍画面、输入代次、账号来源、实训和历战周约束。确定未发送的批次保留意图截图和停止原因，待核对金额归零，本轮停止。已经尝试提交但回执不全时保留原待核对金额，后续刷本入口继续受原账本门禁约束。记录未发送结果写入失败时，保留原待核对意图。

已有确认消耗的中断运行，后续仍须通过原预算门禁。原支付已核对且明确 `--new-battle-run` 后，按剩余次数模式从同账号原计划归档读取已核实的进度。历战继续以当前周额度为准。[验证记录](../VALIDATION.md#2026-11-06-体力计划后项账号与余额核验)

## 计划与本次预算

`Settings.power_plan`为最多1000项的有序列表，每项必须有明确分类、名称、地点与1～9999的整数次数；启用[历战优先周计划](echo-of-war-plan.md)后允许空列表，只执行到期历战与已开启的默认补刷。例如：

```json
[
  {"category":"calyx_golden","target":"回忆之蕾","location":"城郊雪原","count":4},
  {"category":"planar","target":"浴火钢心","location":"永恒圣城","count":3}
]
```

示例名称和地点仍须在当前游戏页面逐行核实，目录或JSON本身不证明当前账号已经解锁。分类使用`calyx_golden`、`calyx_crimson`、`stagnant_shadow`、`cavern`、`echo_of_war`、`planar`，不使用自动推断分类。同名副本按地点分开。

| 设置 | 默认值 | 行为 |
| --- | --- | --- |
| `power_plan` | `[]` | 原始目标；空列表须配合历战优先周计划才可显式执行 |
| `power_plan_enabled` | `false` | 桌面显式选择的模式，只有保存设置才持久化；原生Runner与CLI仍须显式传入计划参数，不因该偏好自行扩大执行范围 |
| `power_plan_keep` | `false` | 跨运行扣除已核实次数，完成条目不再刷；设置中的原次数不变 |
| `power_plan_fill` | `true` | 计划处理后按原默认副本、地点与本次`challenge_count`继续补刷；关闭后不执行默认副本 |
| `stamina_limit` | `240` | 整个日常刷本共用的已有开拓力上限，不是每项各有240 |
| `rounds` | `6` | 每批次数上限，实际还受副本与实时资源限制 |

保留模式每次重复原条目，不沿用消耗模式的已完成次数。消耗模式按本地账号与同一组原目标归属进度，重新排序不重置进度，重复相同条目按各自出现次序保留。修改名称、地点、分类或目标次数会成为不同目标组合；切回原组合仍可找到原进度。默认副本的补刷次数属于本次请求，不扣成另一个长期条目。

本次运行只创建一份`BattleBudget`。先从所需副本读取当前已有体力；如果计划或补刷包含饰品提取，先进入其页面独立读取已有沉浸器，再按用户指定顺序执行。这里只读取资源，不因探测饰品页而提前开战。体力冻结为`min(本次上限, 初始已有体力向下取整到10)`，已有沉浸器最多12，单独记账；余额可缩小，后来增加的沉浸器不扩预算，体力自然恢复也不扩计划。饰品仍使用已有存档和指定完整预设编队。

条目次数可以跨运行保留。历战余响的长期目标可大于3，但本次仍最多3次，并继续核对游戏当前剩余周次数；长期目标不提供新的周额度。明确读取到本周0次时，将原条目记为延期并保留次数；启用补刷可继续默认副本。未读到周次数与明确0次是不同状态，未读到仍停止。体力不足以继续当前条目时保留其余次数；启用补刷时，可将原预算内剩余资源用于默认副本。页面未知、支付未知或实际失败则保留证据，不能用默认副本绕开待核对状态。

`run_status='complete'`表示本次在冻结资源范围内结束，`goal_complete`才表示所有长期条目均已完成。预算用完而长期目标有余数可以正常结束；真实流程失败为partial／failed／stopped，原成功条目和待核对资源分别保留。

## 显式入口与保存

以下是用法说明，本轮未执行这些游戏任务：

```powershell
# plan.json是上述JSON列表；只执行列表，禁用默认副本补刷
.\.venv\Scripts\python.exe -m autohsr --run --power-plan --power-plan-file .\plan.json --no-fill-power-plan
# 复用保存的条目，完成日常后再处理到期周常
.\.venv\Scripts\python.exe -m autohsr --plan --power-plan
# 本次重复固定计划，不扣除消耗模式的历史进度
.\.venv\Scripts\python.exe -m autohsr --run --power-plan --keep-power-plan
```

`--no-keep-power-plan`回到扣除剩余次数的语义，`--fill-power-plan`启用默认补刷。文件与CLI覆盖仅作用本次，不写`config.json`。只有“保存设置”持久化原条目、保留及补刷偏好；执行进度保存在本地账本，不在后台删除或扣减设置中的条目。

`--new-power-plan`明确为同一组原条目另开次数目标，保留原目标及证据；不代表新增体力预算，也不解决原支付未知。上次运行中断且已有确认消耗时，仍须依照原恢复门禁明确新增本次预算；`--new-battle-run`不会绕开体力计划中的未知支付、损坏证据或缺失历史。仅补领奖和只接续原货币战争周常不能使用体力计划参数。

## 记账与失败恢复

每批调用现有`DailyWorkflow.battle`，保留页面、目标、编队、价格、开始挑战和结算波次核验。每项的局部完成次数与全局完成次数分别计算，切换分类不清零总消耗，也不重建预算。付费前核实当前账号、新鲜画面和输入代次，先写意图；可见成功、对应账号及证据完整后，资源与条目次数在同一份`battle-session.json`原子提交。

确认写入失败时，内存恢复为原待核对意图，后续不重发挑战；停止、失焦或换号同样保留未知支付。切换回单副本模式、新目标或新预算均不能清掉这份待核对记录。原失败报告与截图继续保留。

下一份预算写入前，先核对并不可覆盖地归档原账本：

- 消耗模式：`runs/power-plans/<账号摘要>/<目标摘要>/<目标ID>/<运行ID>.json`。
- 固定重复：同一目标摘要下的`repeat/<运行ID>.json`。
- 消耗模式的`current.json`锚定目标ID及最近归档的路径／SHA-256；归档以连续序号、前件引用及逐项累计数组成链。

10月30日后新目录的账号／目标键各采用完整摘要的前32个十六进制字符，完整64字符仍保留在账本并逐份核对，避免普通Windows用户目录下超过路径长度限制。已存在的完整摘要目录继续原位读写；同一归属出现新旧两个目录则停止，不猜测哪一份进度应当保留。没有移动或删除旧证据。

原账本、资源截图、每批前后截图、目标索引或归档丢失／变化时停止，不凭空重建剩余次数。截图与原始账号信息只留本地忽略目录，进度事件不含UID、账号摘要或本机路径。

## 界面对接

生存索引按当前刷本模式显示操作。单副本保留“选用”、次数和挑战设置；体力计划模式将目录操作变为“加入计划／编辑次数”，以分类、名称、地点三项查找原条目，点击后使用同一纸面弹窗填写目标次数。应用新增或更新该条目并启用本次刷本，取消保留原列表和开关，不改默认补刷副本、最多次数、补刷开关或预算。“调整计划”直达设置中的有序列表，返回恢复生存索引；目录页用计划项数与共用预算替代单副本的次数滑条，避免显示修改了实际不会执行的单副本目标。运行中不能编辑；全部编辑只改草稿。

从目录打开时直接聚焦并选中次数，输入后可按Enter应用，Esc取消；设置页原有添加／编辑仍先聚焦副本字段。两种入口共用校验与草稿，已加入状态按当前列表更新，不读取账号完成次数。

列表未选中时只启用添加，首尾禁用不可移动方向；运行期间锁定编辑操作，结束后按当前选择恢复，不把无效操作显示为可用。

桌面在“计划后补刷默认副本”一行提供“更换副本”，直接编辑副本、明确地点和最多次数；上限随分类和本次开拓力预算显示。应用不改动计划条目、不启用刷本或补刷，也不写配置；取消保留草稿。补刷输入错误定位同页入口，只有保存设置才持久化。

桌面入口为“设置 → 体力计划”。原目标列表使用目录中的分类、名称和地点；添加／编辑通过游戏样式弹窗确认，取消不改条目，移除和排序只修改草稿。选择计划模式后，首页日常副本卡改为“调整计划”，显示目标项数与共用上限；不从旧账读取账号未核实的剩余次数。初次载入旧配置即使列表非空也保持单副本模式。模式、原目标、次数处理、默认补刷与历战偏好均在显式保存时写入。

运行卡片详情展示每项原目标、此前已核实、本次已核实与本目标剩余；保存的列表仍为原次数。报告中`run_status=complete`而`goal_complete=false`时，成功结束本次运行不写成全部目标完成。原日常复用在卡片和摘要中明确注明；原货币周常接续不传入`use_power_plan`。CLI用法保持上文显式`--power-plan`，桌面偏好不隐式改变其他调用。

长工作树中的旧64／64目录只在文件访问时使用Windows扩展路径写法，证据引用继续保存普通规范路径；旧目录、索引、哈希与归档链不迁移或重建。新目标继续使用短目录键；读写、不可覆盖归档与计数核对语义不变。

`Runner(settings,...,use_power_plan=True,new_power_plan=False)`只适用于正式日常操作；`PlanRunner`接受相同参数，传递给原日常Runner。仅存有条目不会改变旧GUI或CLI的单副本行为。界面需在明确的多副本模式下传递`use_power_plan=True`，不能只因载入配置发现列表非空而悄悄切换执行范围。

原始报告的`power_plan`保留目标、`before`、本次`done`、初始资源、本次支付、剩余状态及分项结果；父计划报告复制日常原件。`before[i]+done[i]`是当前目标的已核实累计数。首页在未核实当前账号前只展示原计划，不把历史账号的剩余次数当作当前状态。

运行事件`type='power_plan_progress'`包含`stage`（ready／resources／weekly／item／confirmed／complete／partial）、`rows`、`active_row`、`active_count`、全局完成及资源字段。每个row含原条目、`before`、`done`和`remaining`；`active_row=-1`表示默认补刷，`-2`表示到期历战优先阶段。可选`weekly_echo`提供原目标周、状态、当前已知余数和本次完成，未开启时为null；`goal_complete`只指用户长期条目。confirmed事件只在账本成功提交后发送，事件为快照；PlanRunner继续附加daily阶段，不覆盖周常或原日常结果。此接口不要求更换现有GUI框架。

## 培养目标读取入口

在已登录的简体中文游戏客户端中打开「星际和平指南 → 生存索引」，使左侧「培养目标」可见。可使用开发版桌面的「打开培养目标」，也可从源码目录运行下列命令。日常继续按原单副本或显式体力计划运行。

```powershell
.\.venv\Scripts\python.exe -m autohsr --read-build-target
```

入口复用 Runner 的窗口、执行权、暂停停止和既有待核对门禁。普通目录须有一条与随包目录一致的完整副本行和唯一可见的左栏入口。两张同账号、同窗口几何、同代次的新鲜画面核实来源。先留图，完成坐标计算和窗口检查后，在原生发送前重新核实同一入口、账号、输入代次及画面时效。已在培养目标页时直接观察。到页需要连续两张无遮挡的新帧，可由右侧「培养还需获取资源」或完整的「角色培养」状态、推荐及设置区共同证明。短暂空帧、账号漏读或同一行相邻 OCR 片段拼成的登录提示与材料弹层会打断配对。换号、代次改变、窗口移动、证据写入失败或观察超出限次均停止。

`report.json` 的 `build_target.entry_input` 分开记录未发送、已发送和发送结果不明，`page_verified` 表示观察到培养目标页。截图文件名可在本次报告目录内定位，原始截图及 OCR 保存在本地运行目录。该操作以到页核实为完成条件，刷本次数、开拓力、沉浸器均为零。仅识别推荐遗器、空白或遮挡时，结果保持未核实。

命令输出的 `status=success` 与 `build_target.draft.state=prepared` 表示草稿已发布。`build_target.draft.file` 指向 `run_dir` 内的新建 `power-plan.json`，内容只有一条分类、名称、地点和次数。`count_source=manual` 表示轮次为用户手填，`stamina_required` 是按目录费用算出的预计开拓力。草稿阶段开战、支付及游戏输入均为零。该草稿的材料缺口、单轮产量和实际预算留空。

本次 `report.json` 先保存 `partial/staged` 审计回执，记录所选条目、草稿 SHA-256 和所引用的原始截图。最终草稿随后在同一 NTFS 运行目录独占发布，磁盘回执保留在 `staged` 阶段。同名文件保留原样，截图或回执发生变化、停止或发布失败时，命令返回失败或停止并保留已有记录。旧同名文件即使字节相同，也可能让 `staged` 回执与现有文件哈希一致。应核对本次命令的 `success/prepared` 输出和当前草稿哈希来确认本次发布。

审阅草稿后，如要执行，先在游戏内返回可识别的普通导航页，再显式运行既有体力计划。仅刷这一个副本时，使用已启用刷本和已有资源消耗、且已关闭其他日常任务的配置。下面的选项关闭默认补刷和历战，并把草稿的次数用于本次明确的固定计划。

```powershell
if ($draft.status -ne 'success' -or $draft.build_target.draft.state -ne 'prepared') { throw '培养草稿未发布' }
$planFile = Join-Path $draft.run_dir $draft.build_target.draft.file
if ((Get-FileHash -LiteralPath $planFile -Algorithm SHA256).Hash -ne $draft.build_target.draft.sha256) { throw '培养草稿与本次回执不同' }
.\.venv\Scripts\python.exe -m autohsr --run --power-plan --power-plan-file $planFile --keep-power-plan --no-fill-power-plan --no-echo-of-war
```

正式运行按当前账号、副本、支援设置及实际已有开拓力复核，原待核对支付仍会阻止新预算。核对该行 `power_plan.done[0]` 和本次对应支付回执判断实际完成次数。旧目标进度或 CLI 的 `success` 可能对应本次零开战。材料补足仍需读取实际掉落或新的培养缺口。
